AI-Powered Voter Database Assistant

Turning a 4-million-record SQL Server database into something a non-technical user can just ask questions to

A 4+ million record SQL Server voter database (bocogop, 72 tables) is powerful, but useless to anyone who doesn't write SQL. This project puts a plain-English chat interface in front of it — Streamlit for the UI, LangChain orchestrating the pipeline, and Claude handling both the SQL generation and the result interpretation, so a non-technical user can just ask a question and get a real answer.

1. Built a Two-Stage AI Pipeline

Rather than one model call trying to do everything, the pipeline splits the work into two clear stages: Claude first turns the plain-English question into a SQL query, the query runs against the actual database, and then Claude takes the raw results and turns them back into a natural, readable answer — closing the loop from question to plain English again.

  • Stage 1: Claude generates the SQL from the user's question
  • Stage 2: SQLAlchemy + pyodbc execute it against SQL Server
  • Stage 3: Claude interprets the raw results into a conversational answer

2. Connected Securely Over SSH

The database sits on a remote server, not open to the internet. Access goes through a PuTTY SSH tunnel with key-based authentication (no passwords), so the app talks to 127.0.0.1 locally while the actual traffic is encrypted end to end to the real database server. The connection detail that trips people up most: the SSH tunnel has to be running before the app starts, or the database connection just fails.

3. Fixed a Recurring Schema Bug

bug fix

Claude would sometimes generate SQL referencing a table by its bare name, which failed since every table actually lives under the dbo schema. Fixed with a two-part solution: explicitly instructing the model to always use the full dbo.TableName format, plus an automatic fallback that retries with the prefix added if a query fails on a missing table.

-- Before: fails
SELECT COUNT(*) FROM Voter

-- After: works
SELECT COUNT(*) FROM dbo.Voter

4. Diagnosed and Fixed a Speed Problem

performance

Queries were taking around 10 seconds normally, with one spiking to a brutal 66 seconds. The fix wasn't infrastructure — it was model choice. Claude Sonnet was doing both the SQL generation and the result interpretation, and most of that time was pure model latency, not the database itself (the SSH tunnel + query execution was only about 2 seconds of the total).

Switching both pipeline stages from Claude Sonnet to Claude Haiku cut response time roughly in half, with no meaningful quality loss for SQL generation — the task doesn't need Sonnet's extra reasoning depth, just speed and consistency.

~10s (worst case: 66s) → ~5s

5. Added Conversation Memory

The first version treated every question as a fresh start, which meant no natural follow-ups. Adding memory of the last 5 exchanges lets a user ask something like "which zip codes have the most voters," then follow up with "what's the party breakdown" — and the assistant correctly infers that the second question means within those same zip codes, without having to repeat the context.

Result

Plain-English question → Claude generates SQL → query runs securely over SSH → Claude interprets the results → conversational answer, with memory of what was asked before

A non-technical user can now explore a 4-million-record database the same way they'd ask a colleague a question — no SQL knowledge required, answers in under 5 seconds, and a UI that remembers the conversation instead of resetting with every question.
